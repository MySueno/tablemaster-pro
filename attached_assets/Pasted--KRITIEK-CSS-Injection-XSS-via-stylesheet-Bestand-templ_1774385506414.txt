🔴 KRITIEK — CSS Injection (XSS via stylesheet)
Bestand: templates/table-frontend.php, regels 48–62
Alle kleurvariabelen worden zonder escaping rechtstreeks in een <style>-blok geprint:
php--tmp-header-bg: <?php echo $header_bg; ?>;
sanitize_hex_color() filtert dit af tot een geldige hex-kleur, maar als een aanvaller die functie omzeilt (bijv. via een race condition bij import, of een toekomstige bug in de sanitizer), kan willekeurige CSS of zelfs JavaScript via expression() worden geïnjecteerd in oudere browsers. De juiste aanpak is esc_attr() ook hier toepassen, zelfs als de waarden al gesaniteerd zijn. Defense-in-depth ontbreekt volledig op deze 15 regels.

🔴 KRITIEK — SSRF via Update Server URL
Bestand: includes/class-settings.php + includes/class-updater.php
Een beheerder kan willekeurig een URL instellen als "update server". De updater doet vervolgens een wp_remote_get() naar die URL zonder enige beperking van het schema, het IP-bereik of de host. Dit maakt Server-Side Request Forgery (SSRF) mogelijk: een aanvaller met beheerderstoegang (of via CSRF) kan de server verzoeken sturen naar interne netwerkadressen (http://169.254.169.254/ voor AWS metadata, http://localhost/, etc.).
Het is ook opmerkelijk dat de update-server URL in de database wordt opgeslagen en bij elke plugin-load wordt uitgelezen om TMP_UPDATE_URL te definiëren — vóór authenticatie wordt gecontroleerd.

🟠 HOOG — SQL Injection risico via onbeschermde IN()-queries
Bestand: includes/class-db.php, regels 447 en 575
php$in = implode( ',', array_map( 'intval', $row_ids ) );
$wpdb->query( "DELETE FROM ... WHERE row_id IN ($in)" );
De array_map( 'intval', ... ) mitigeert het risico grotendeels, maar $row_ids komt rechtstreeks uit $wpdb->get_col() en wordt niet verder gevalideerd. Dit patroon is technisch veilig zolang intval() integer-overflow niet toelaat — maar het is een antipatroon dat door WordPress zelf wordt afgeraden. $wpdb->prepare() ondersteunt geen IN()-placeholders, maar de aanbevolen methode is dynamische placeholders bouwen. Dit is een toekomstig onderhoudsrisico.

🟠 HOOG — Row-content sanitization is inconsistent
Bestand: includes/class-ajax.php (save_structure), includes/class-db.php (save_table_structure)
In class-ajax.php worden rijen alleen op lengte gecontroleerd zonder sanitering:
php// Geen sanitering van individuele celinhoud in save_structure() in class-ajax.php
De sanitering vindt pas later plaats in save_table_structure() via wp_kses_post(). Dit is afhankelijk van de volgorde van aanroep. Als de opslaagroute ooit verandert of rechtstreeks wordt aangeroepen, valt de sanitering weg.

🟡 GEMIDDELD — Geen rate limiting op AJAX-endpoints
Alle AJAX-acties (opslaan, dupliceren, zoeken) hebben geen rate limiting. De search_posts-actie voert een WP_Query uit met een s-parameter voor elke aanvraag. Een geauthenticeerde gebruiker met manage_options kan hiermee de database herhaaldelijk bevragen.

🟡 GEMIDDELD — col->type niet gewhitelistd bij opslaan
Bestand: includes/class-db.php (save_table_structure)
php'type' => sanitize_text_field( $col['type'] ),
sanitize_text_field() is geen whitelist. Het kolomtype kan willekeurige strings bevatten. In het frontend-template wordt $col->type gebruikt als data-col-type attribuut — wel correct ge-escaped — maar het type bepaalt ook renderlogica (link, image, html). Een onverwacht type als html in combinatie met de inline_html-instelling kan onbedoeld HTML renderen.

🟡 GEMIDDELD — uninstall.php gebruikt raw SQL zonder prepare()
php$wpdb->query(
    "DELETE FROM {$wpdb->options} WHERE option_name LIKE '_transient_tmp_data_%' ..."
);
De prefix $wpdb->prefix is een bekende veilige waarde, maar het patroon stelt een slechte norm. Bij uitbreiding of copy-paste kan dit tot echte injecties leiden.
